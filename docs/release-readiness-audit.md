## Architecture Decisions

- Keep `main.tsx` as the startup boundary only.
- Keep notification sources mounted at `AppShell` level so in-app toasts are not tied to visible page components.
- Keep browser notification smoke hooks loopback-only and sample-data based; they are verification aids for the local built app, not production user-facing controls.
- Keep page-owned pure helpers beside page folders before extracting full components.
- Keep `server.mjs` monolithic until each moved route group has injection-friendly helpers and route/persistence tests that preserve auth, CSRF, cache, and background-job behavior.
- Keep normal page rendering on live BitJita data through the local proxy; SQLite remains the source for history, notifications, analytics, diagnostics, cached tools, and admin/server state.
- Prefer last-known-good or cached helper data only when the UI clearly shows freshness or stale state.

## Server Architecture Audit Notes

`server.mjs` is still the largest release-readiness risk. The current file has several stable conceptual regions that can become modules, but most of them share the same SQLite handle, prepared statements object, settings helpers, rate-limit maps, cache maps, and request helpers. Splitting by copying chunks would be risky; the safer path is dependency-injected modules that receive a small server context instead of importing global state directly. The first extracted helpers, `src/server/httpRoutes.mjs`, `src/server/httpResponses.mjs`, `src/server/httpCookies.mjs`, `src/server/httpRequests.mjs`, `src/server/httpCsrf.mjs`, `src/server/httpBodies.mjs`, `src/server/httpRateLimit.mjs`, `src/server/visitorIp.mjs`, `src/server/notificationActivity.mjs`, `src/server/dealAlerts.mjs`, `src/server/marketActivity.mjs`, `src/server/productionActivity.mjs`, `src/server/recipeCatalog.mjs`, and `src/server/scheduledJobs.mjs`, are intentionally dependency-light and own route classification, static-asset visitor logging decisions, security headers, static cache policy, frontend MIME type mapping, JSON/text/binary response writers, cookie parsing, HttpOnly session-cookie serialization, request-origin derivation, same-origin checks, safe return-path handling, admin CSRF token matching, body-size limits, raw request-body reading, JSON parsing, body-too-large errors, route rate-limit policies, request-address extraction, 429 limiter behavior, visitor IP normalization, coarse anonymization, app-salted visitor IP hashing, public notification metadata redaction, public deal-alert/Discord payload formatting, market activity normalization/source-key logic, production craft identity/metrics/profession-key logic, recipe catalog target normalization, and scheduled-job schedule parsing/serialization/labels.

Current evidence:

- Environment, data-directory setup, SQLite schema creation, migrations, seeded defaults, and prepared statements live near the top of `server.mjs`. The prepared statement block mixes settings, admin sessions, app user sessions, analytics, production, market, Discord delivery, moderation, scheduled jobs, and cached payloads.
- Route classification, static-asset visitor logging, security headers, frontend MIME types, and static cache policy now live in `src/server/httpRoutes.mjs`; JSON/text/binary response writers now live in `src/server/httpResponses.mjs`; cookie parsing and HttpOnly session-cookie serialization now live in `src/server/httpCookies.mjs`; request-origin, same-origin, and safe-return-path helpers now live in `src/server/httpRequests.mjs`; CSRF token derivation and header matching now live in `src/server/httpCsrf.mjs`; body limits, raw request reading, JSON parsing, and body-too-large errors now live in `src/server/httpBodies.mjs`; rate-limit policies, request-address extraction, and 429 limiter behavior now live in `src/server/httpRateLimit.mjs`; visitor IP normalization, coarse anonymization, and app-salted IP hash creation now live in `src/server/visitorIp.mjs`; public notification-activity metadata redaction now lives in `src/server/notificationActivity.mjs`; market deal-alert row formatting and Discord payload formatting now live in `src/server/dealAlerts.mjs`; market listing normalization, BitJita timestamp coercion, trade/listing matching, and market event source-key helpers now live in `src/server/marketActivity.mjs`; production craft identity, output lookup, metrics, and profession-key helpers now live in `src/server/productionActivity.mjs`; recipe catalog key and target normalization helpers now live in `src/server/recipeCatalog.mjs`; scheduled-job schedule parsing, serialization, next-run calculation, and labels now live in `src/server/scheduledJobs.mjs`. Focused tests cover admin, auth, Discord, BitJita proxy, local API, static asset, app-route classifications, release security headers, frontend asset response policy, response writer headers/bodies, cookie parsing, cookie attributes, origin derivation, same-origin behavior, redirect path safety, CSRF token matching, body-size limit policies, streamed body concatenation, empty-body JSON defaults, 413 body-too-large errors, request-address selection, public route rate-limit policies, bucket reset behavior, 429 retry headers, loopback/IPV4-mapped normalization, IPv4/IPv6 anonymization, app-salted visitor IP hashing, recursive sensitive-key notification metadata redaction, deal-alert public/Discord payload formatting, market listing identity/timestamp normalization, trade/listing matching, market event source-key behavior, production craft stable identity, production metrics/profession-key behavior, recipe catalog key/target normalization, and scheduled-job schedule parsing, clamping, serialization, next-run, and label behavior.
- Authentication and security helpers are already clustered enough to extract later: admin session lookup, app user sessions, Discord OAuth, role permissions, same-origin checks, and CSRF checks are near each other.
- Discord behavior is large and mixed: message delivery, role panels, moderation, custom commands, component handling, OAuth-backed admin/user state, and interaction handling are in one file but mostly grouped by function families.
- Collector and scheduled-job behavior is also grouped enough to split later: recipe catalog refresh, GeoIP refresh, market deal watch jobs, regional buy-order baselines, production contribution collection, storage activity, current-claim refresh, and server snapshot polling are identifiable domains.
- The main `createServer` dispatcher is an ordered route chain. Public health/proxy/config endpoints must remain before admin routes; static frontend fallback must remain after API handling so API typos do not return `index.html`.

Current automated coverage that protects a future split:

- `test/server-route-groups.test.mjs` covers the extracted route classification helper directly.
- `test/server-http-bodies.test.mjs` covers body-size limits, streamed raw-body reading, JSON parsing, and 413 body-too-large errors directly.
- `test/server-http-rate-limit.test.mjs` covers request-address extraction, route rate-limit policies, bucket windows, and 429 retry response behavior directly.
- `test/server-visitor-ip.test.mjs` covers visitor IP normalization, anonymization, and app-salted hash format directly.
- `test/server.test.mjs` starts the real server in a child process with an isolated data directory and mocked upstream BitJita service.
- The integration test covers security headers, BitJita proxy cache/dedupe/stale-if-error behavior, cached local helper endpoints with freshness metadata, admin setup/login/roles/CSRF, scheduled jobs, GeoIP, analytics, market deal watches and alerts, polling, activity/history, production data protection, notification-activity filtering, notification metadata redaction, and the extracted notification-activity helper boundary.
- A separate background-polling test verifies upstream failures do not terminate the server process.

Recommended split order:

1. Move SQLite schema/migrations and prepared statements into a database module that returns `{ db, statements }`; do not let route modules open their own database handles.
2. Extract auth/session/permission helpers with tests for owner/admin/viewer behavior and same-origin/CSRF rejection.
3. Extract the BitJita proxy/cache module with the existing cache, dedupe, stale-if-error, timeout, and response-header tests preserved.
4. Extract scheduled jobs and collectors behind a small service API so long-running work remains outside request lifetimes.
5. Extract Discord service functions separately from admin route handlers; keep real Discord delivery mocked or disabled in tests.
6. Split the route dispatcher last into small route modules registered in the same order as today.

Do not split `server.mjs` further until a fresh server test run passes after each step. Any route extraction should keep admin mutations behind `requireAdmin`, `requireAdminMutation`, and `requireAdminPermission`; preserve the public/private distinction for app user endpoints; keep bot tokens and OAuth secrets out of public settings responses; and keep expensive API-heavy work behind cache/rate-limit/background-job boundaries.
